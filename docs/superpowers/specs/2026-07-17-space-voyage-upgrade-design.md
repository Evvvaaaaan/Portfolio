# Space Voyage Upgrade — 우주 항행 경험 심화 설계

날짜: 2026-07-17
상태: 승인됨 (2026-07-17)

## 목표

포트폴리오를 "고퀄리티, 전문적인 3D 웹사이트"로 끌어올린다. 방향은 **현재
우주 테마의 심화**: 사이트 전체를 "방문자가 우주선을 타고 섹션(좌표)들을
항행한다"는 하나의 서사로 묶는다. 로딩은 워프 진입, 섹션 전환은 워프 항행,
각 섹션은 서로 다른 우주 좌표 도착이다.

사용자가 지목한 우선 개선 영역은 (1) 전환/인터랙션 완성도, (2) 첫인상(Hero)
임팩트다. 배경 밀도는 그다음이다.

## 접근 선택 (논의 결과)

세 가지 접근 중 **A. 레이어드 심화**로 확정:

- **A. 레이어드 심화 (선택)** — 현재 아키텍처(고정 캔버스 배경 + DOM
  슬라이드덱) 유지, 세 개 축을 단계별로 업그레이드. 각 단계 독립 배포 가능,
  진행 중인 `feat/warp-scroll-transition` 브랜치가 그대로 1단계 기반.
- B. 원-캔버스 여행형 — 스크롤 시스템 재구축, 카메라가 연속된 3D 공간을
  비행. 임팩트 최대지만 몇 주 규모 + 접근성/모바일 어려움. 폐기(추후 별도
  프로젝트로 재검토 가능하며, A의 자산은 B에서 재사용된다).
- C. 포스트프로세싱 + 마이크로 인터랙션만 — 빠르지만 "전환이 아쉽다"는 근본
  문제를 못 풂. 단독 폐기하되 광택 요소는 A의 Phase 1에 흡수.

## 현재 상태 진단

배경(`SpaceBackground`: 순수 Three.js 별필드 + warp 줌), 콘텐츠(App.jsx의
DOM 슬라이드덱, scale/blur 전환), Hero(자체 파티클 + 타이핑)가 **각자 따로
노는 3개 레이어**다. warp 브랜치가 배경과 스크롤을 연결하기 시작했지만
아직 하나의 경험으로 묶이지 않았다.

## Phase 1 — 워프 전환 완성

진행 중인 `feat/warp-scroll-transition` 브랜치의 연장.

- **하이퍼스페이스 스트릭**: warp intensity 정점에서 별이 카메라 방향으로
  선처럼 늘어난다. 별 파티클을 커스텀 셰이더(ShaderMaterial)로 전환하고
  intensity uniform으로 신축을 제어.
- **포스트프로세싱 (데스크톱 전용)**: 은은한 블룸 + warp 정점에서만 걸리는
  방사형 블러/색수차. 드라이버는 동일한 intensity.
- **DOM 동기화**: 현재 슬라이드 blur/scale(App.jsx)과 카메라
  warp(SpaceBackground)가 각자 스크롤을 읽는다. 이미 순수 함수로 분리된
  `computeTransitionIntensity`를 단일 소스로 삼아 두 레이어의 타이밍 커브를
  일치시킨다.
- **섹션별 우주 좌표**: 섹션마다 배경 색조(성운/포그 틴트)가 달라져 전환할
  때마다 "다른 곳에 도착"한 느낌을 준다. 색조 보간은 순수 함수로 분리.

## Phase 2 — Hero 도착 시퀀스 (첫인상)

- 첫 로딩 시: 카메라가 고속 워프 상태(스트릭 최대)에서 시작 → 감속하며
  Hero 별필드에 정착 → 정착이 끝나는 순간 타이틀/타이핑이 스태거로 등장.
- 기존 LoadingShowcase와 자연스럽게 이어붙인다 (로딩 종료 = 워프 감속 시작).
- `prefers-reduced-motion`이면 시퀀스를 생략하고 정착 상태로 바로 시작.

## Phase 3 — 배경 밀도

- **셰이더 성운**: FBM 노이즈 기반 성운 플레인 2~3장, 느린 드리프트,
  Phase 1의 섹션별 색조와 연동.
- **시차 별 레이어**: 별을 깊이 밴드 2~3개로 나눠 크기/이동속도 차등 →
  깊이감. (현재도 z 분포는 있으나 단일 레이어.)
- **모바일(중간 수준)**: 별 수 축소 + 저해상도 성운은 모바일에도 적용.
  포스트프로세싱/워프는 데스크톱 전용(현행 유지).

## 아키텍처 원칙

- `SpaceBackground`는 현재의 순수 Three.js 유지 (R3F 전환 없음 — 잘 작동하고
  가벼움). 새 요소는 같은 폴더의 독립 모듈로 추가:
  `nebula.js`, `warpStreaks.js`, `postfx.js` — 각각 `create/update/dispose`
  인터페이스를 갖는다.
- 순수 계산(intensity, 색조 보간, 도착 시퀀스 타임라인)은 렌더 루프와 분리해
  유닛 테스트 가능하게 둔다 (기존 `transitionIntensity.js` 패턴).
- **성능 예산: 데스크톱 120fps** (고주사율 디스플레이 기준, rAF 언캡 — 프레임
  당 ~8.3ms 예산). DPR ≤ 2 유지. 모바일은 DPR ≤ 1.5 + 파티클 감축으로 60fps.
  포스트프로세싱 패스는 120fps 예산 안에 들어오는지 실측 후 채택 여부 결정
  (예산 초과 시 해당 패스만 강도 축소 또는 제외).

## 테스트

- Vitest: 순수 함수(intensity 확장, 색조 보간, 시퀀스 타임라인) 단위 테스트.
- Playwright 스모크: 메인 페이지 렌더 + 콘솔 에러 없음.
- 수동 확인(브라우저): 워프 스트릭/포스트프로세싱 시각 품질, 120fps 유지
  여부(DevTools 성능 패널), 모바일 회귀 없음, reduced-motion 동작.

## 진행 순서

Phase 1 → 2 → 3. 각 Phase는 독립적으로 머지/배포 가능. 현재
`feat/warp-scroll-transition` 브랜치를 마무리한 뒤 그 위에 쌓는다.

## 범위 외

- 원-캔버스 여행형(B) 전환 — 추후 별도 스펙.
- 모바일에서의 워프/포스트프로세싱 — 요청 시 별도 스펙.
- 섹션 콘텐츠(About/Skills/Projects 카드 레이아웃) 자체의 재디자인.
