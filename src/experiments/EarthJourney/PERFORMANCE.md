# Terra 성능 검증

측정일: 2026-09-15. 경로: `/gallery/terra`.

## 지도 화면 연속성 수정 (2026-09-15 후속 검증)

AI 이미지 패널을 제거하고 파리를 포함한 모든 목적지를 실제 3D 지도로 통일했다.
생성한 PNG 원본은 `public/terra`에 보관하지만 화면에서 요청하지 않는다.

로딩을 지연시킨 재현에서는 표시 타일이 0개인데도 카메라가 270m까지 내려가
지면이 단색으로 보였다. 파리 출발 직후에도 패널이 사라지면서 준비되지 않은
501m 시야가 노출됐다. 현재는 지형이 없으면 약 2,870km의 지구본 시야를 유지하고,
표시 가능한 지역의 타일 정밀도에 맞춰 최소 고도를 로그 보간하여 접근한다.
지구본은 지형 아래에 남겨 타일 사이의 빈 부분을 받친다.

파리 지도 선행 로딩을 복구했으며, 현재 지형이 준비되고 가까이 접근한 뒤 다음
목적지로 선행 로딩을 넘긴다. 궤도 이탈 시 수평 카메라 구도가 갑자기 바뀌던
분기도 연속 보간으로 변경했다. 화면의 타일 개수는 로딩용 카메라 등록 여부와
분리하여 실제 표시 카메라의 시야로 계산한다.

스크롤 위치만으로 도착을 선언하지 않는다. 지도 준비와 실제 접근이 끝나기 전에는
`approach` 상태를 유지하고, 빈 지형의 둘러보기 버튼은 표시하지 않는다. 따라서
성능 검사의 도착 기준도 고정 구간 0.84가 아닌 실제 `arrived` 표시로 변경했으며,
지도 없이 도착 상태를 표시한 횟수는 두 조건 모두 0회였다.

| 후속 측정 조건 | 파리 렌더 제출 FPS | 로마 렌더 제출 FPS | 50ms 이상 긴 작업 |
| --- | ---: | ---: | ---: |
| 데스크톱 1440×960, Metal | 125.24 | 125.34 | 0건 |
| 390×844, CPU 4배 감속, 6Mbps·150ms | 119.37 | 119.53 | 0건 |

이는 Chromium의 CPU 측 렌더 제출 빈도이며 실제 디스플레이 출력 보장이 아니다.
모바일 제한 조건에서는 로마 지형이 8초 이동 구간 안에 준비되지 않았다. 이때는
지구본을 유지하며 스크롤을 계속 처리하고, 실제 도착으로 표시하지 않는다.
아래 수치는 이 수정 이전의 검증 기록이다.

## 적용 사항

- 25ms 렌더 제한을 제거했다. 움직임이나 새 지형이 있을 때 매 `requestAnimationFrame`마다 그리며, 정지 화면은 불필요하게 다시 그리지 않는다.
- 스크롤 카메라의 시간 기반 추종 계수를 7에서 22로 높여 지연을 줄였다. 화면 주사율에 따라 이동 속도가 달라지지 않는다.
- 진입 즉시 지구 텍스처와 파리의 도착 시점 카메라로 지형을 준비한다. 도착하면 다음 목적지를 준비하고, 다른 목적지로 이동하거나 화면 크기가 바뀌면 준비 대상도 갱신한다.
- 선행 로딩 카메라의 해상도·구도·정밀도를 실제 도착 화면과 맞췄다. 화면 밖 지형은 실제 그리기에서 제외한다.
- 지형 선택은 약 50ms 간격의 별도 작업이다. 이 간격은 렌더링이나 스크롤에 적용되지 않는다. 궤도 카메라로 지구 전체의 3D 타일을 요청하지 않는다.
- 다운로드·파싱·노드 처리에는 Terra 전용 큐를 사용한다. 파싱은 한 번에 하나씩 처리하고, 빈 시간에 셰이더 컴파일과 모델별 GPU 텍스처 업로드를 수행한다. 다른 Lab 작품의 공용 큐 설정은 변경하지 않는다.

## 1차 데스크톱 측정 방법과 결과

macOS의 Chromium headless + ANGLE Metal, 1440×960, 로컬 Vite 개발 서버와 실제 Google Maps 3D Tiles를 사용했다. 인위적으로 프레임 시간을 만들거나 지도 응답을 대체하지 않았다. 브라우저의 실제 프레임 콜백은 약 120Hz였다.

새 브라우저 문맥에서 진입 후 5초를 기다리고, 각 이동 구간을 8초 동안 동일한 스크롤 경로로 진행했다. `requestAnimationFrame` 간격, 해당 캔버스의 WebGL 화면 지우기 호출, 콜백 실행 시간, Long Tasks API를 계측했다. FPS는 CPU 측 렌더 제출 빈도이며, 물리적 디스플레이 출력이나 GPU 완료 시간을 보장하는 수치는 아니다.

| 항목 | 최적화 전 | 1차 측정 |
| --- | ---: | ---: |
| 지구에서 파리까지 렌더 FPS | 31.61 | 120.05 |
| 파리에서 로마까지 렌더 FPS | 31.73 | 119.85 |
| 파리 구간 렌더 간격 95백분위 | 33.8ms | 11.6ms |
| 로마 구간 렌더 간격 95백분위 | 34.1ms | 11.9ms |
| 진입 후 5초간 지도 요청 | 0건 | 414건 |

1차 측정의 두 이동 구간에서는 지도 요청 1,111건이 발생했다. 다운로드 또는 파싱이 진행 중인 상태에서도 각각 508프레임과 879프레임을 관측했다. 프레임 콜백의 최대 간격은 두 구간 모두 10.4ms였으며, 50ms 이상 긴 작업은 0건이었다.

카메라 경로는 각 구간의 0.84 지점부터 도착 상태다. 출발지 지형을 제외하기 위해 구간 후반부터 목적지 지형 표시를 검사했으며, 파리는 0.501, 로마는 0.629 지점에서 이미 표시되고 있었다. 별도 여행 검사에서도 스크롤 전 파리의 지형 준비와 각 도착 지점에서 다음 목적지로 선행 로딩 대상이 바뀌는 것을 확인했다.

중간 프로파일링에서는 첫 지형 표시 시 GPU 텍스처 업로드가 한꺼번에 발생하며 94ms의 긴 작업이 관측됐다. 모델이 아직 화면에 붙지 않은 상태에서도 업로드하고 실제 도착 카메라와 같은 정밀도로 준비하도록 수정한 후, 두 번의 후속 측정에서 해당 긴 작업이 관측되지 않았다.

이 결과는 위 환경과 두 구간의 관측값이다. 느린 네트워크, 다른 GPU, 즉시 먼 목적지로 건너뛰는 경우에는 도착 시 추가 로딩이 필요할 수 있다. 지도 준비를 기다리기 위해 스크롤을 잠그거나 멈추지는 않는다. 정밀 지형은 준비되는 대로 교체된다.

## 추가 안정성 검증

다음 세 문제를 브라우저에서 재현하고 수정했다.

- 모션 최소화 상태에서 구간 중간을 스크롤한 뒤 둘러보기를 켜면, 표시 중인 목적지가 아닌 실제 스크롤 경로 좌표로 궤도 중심이 바뀌었다. 현재 화면을 그린 카메라 프레임을 그대로 사용해 전환 전후 위치를 유지한다.
- 초기 지도 연결은 성공했지만 하위 지형 요청이 모두 실패하면 로딩 상태가 끝나지 않았다. 진행 중인 요청과 표시 가능한 지형이 모두 없는 실패 상태를 감지해 지구본과 재연결 안내를 표시한다.
- GPU의 준비 완료 응답이 늦는 조건에서 페이지를 떠나면 `compileAsync`의 내부 확인 타이머가 폐기된 프로그램을 읽어 `isReady` 오류가 발생했다. 빈 시간에 현재 하늘 화면과 지상 안개 화면의 셰이더를 미리 컴파일하되, 수명이 긴 내부 확인 타이머는 사용하지 않는다. 목적지를 빠르게 네 번 변경하고 페이지를 나갔다 돌아오는 과정을 세 번 반복하는 회귀 검사로 확인한다.

성능 검사에는 390×844 화면, CPU 4배 감속, 다운로드 6Mbps·업로드 2Mbps·지연 150ms 조건을 추가했다. 이는 데스크톱 Chromium의 제한 조건 시뮬레이션이며 실제 휴대폰 GPU·발열·배터리 환경의 측정은 아니다. 느린 회선에서 도착 전 정밀 지형 완성을 보장하는 검사는 하지 않는다. 지도 다운로드 중 프레임 제출이 이어지는지와 지구로 복귀하는 조작이 가능한지를 검사한다.

사전 준비와 종료 처리를 보완한 뒤, 프로파일러 없이 전체 스위트에서 측정한 결과는 다음과 같다.

| 최종 측정 조건 | 파리 구간 렌더 FPS | 로마 구간 렌더 FPS | 두 구간의 50ms 이상 긴 작업 |
| --- | ---: | ---: | ---: |
| 데스크톱, 회선 제한 없음 | 119.86 | 119.97 | 0건 |
| 모바일 크기, CPU 4배 감속, 6Mbps·150ms | 116.60 | 117.78 | 0건 |

모바일 제한 조건에서는 지도 요청 229건이 이동 중 발생했고, 다운로드 또는 파싱 중인 상태의 프레임을 각각 936회·943회 관측했다. 최대 프레임 콜백 간격은 25.2ms·17.6ms였다. 최초 제한 조건 검사에서는 89ms의 긴 작업이 한 번 관측됐으므로, 최종 관측값을 모든 실행에서 지연이 없다는 보장으로 해석해서는 안 된다. 회선·로드 시점에 따라 도착 직후에는 기본 지형만 보이고 정밀 지형이 계속 로딩될 수 있다.

최종 검증은 브라우저 검사 11개, 단위 테스트 474개, 대상 파일 정적 검사, 프로덕션 빌드가 모두 통과했다. 종료 검사는 GPU 준비 완료 확인을 의도적으로 지연시키며, 마지막 측정에서는 세 번의 재진입 동안 뒤늦은 오류와 페이지 종료 후 추가 지도 요청이 발생하지 않았다.

## 재실행

기존 `VITE_GOOGLE_TILES_KEY`가 설정된 환경에서 실행한다. 키를 출력하거나 테스트 결과에 저장하지 않는다.

```sh
npm run test:e2e -- --config=playwright.terra.config.js
npm test
npm run build
```

성능 검사만 실행하려면 다음 명령을 사용한다. 실행 결과의 `frame-performance.json`에 원시 측정값이 저장된다. macOS에서는 전용 설정이 Metal을 사용한다. 다른 운영체제에서는 브라우저의 기본 그래픽 백엔드를 사용하므로 별도의 실측이 필요하다.

```sh
npm run test:e2e -- e2e/terra-performance.spec.js --config=playwright.terra.config.js
```

모바일 제한 조건만 실행하거나 CPU 프로파일을 저장할 수도 있다. 프로파일링을 켜면 계측 오버헤드가 추가되므로 일반 성능 결과와 구분한다.

```sh
npm run test:e2e -- e2e/terra-performance.spec.js --grep 'mobile constrained' --config=playwright.terra.config.js
TERRA_PROFILE=1 npm run test:e2e -- e2e/terra-performance.spec.js --grep 'mobile constrained' --config=playwright.terra.config.js
```

1차 검증은 브라우저 검사 7개, 단위 테스트 474개, 대상 파일 정적 검사, 프로덕션 빌드가 통과했다. 기존 Three.js 공용 번들의 크기 경고는 남아 있다. 수정 전 전체 단위 검사에서는 작업 범위 밖의 `dev/fittingService.test.js`가 한 차례 `Expected: SOURCE_EXPIRED / Received: BUSY`로 실패했으며, 해당 파일을 변경하지 않고 재실행한 이후 검사는 통과했다.

추가로 낮은 가로 화면에서 버튼이 잘리던 배치와, 지도 연결 실패 후 지구본이 다시 그려지지 않던 문제를 회귀 검사로 확인하고 수정했다.
